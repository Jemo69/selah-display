Executive

What it is

Sermon Assist is an opt-in feature of the Selah control app. A local speech engine (or a deliberate cloud / LAN engine) transcribes a segment, and a deterministic detector proposes a Bible reference, a next lyric line, and a note. A proposal reaches a screen only after the operator presses its own send action.

The design default is local: the engine binds loopback, the model files never leave the computer, and the feature is cold until explicitly enabled.

Current verdict

8overall / 10
0%benchmark WER
0OS finals on 24 min

The local pipeline is real, end-to-end, and verified with actual church audio. Cloud and LAN have real implementations in PR #86, but neither has been validated against a live provider or a second physical machine. OS on-device is safe but not usable on the real recording.

Production sentence: ready for a controlled local church pilot; not ready to promise general production until a production model and the target hardware are validated. Cloud/network are architecture + unit proof, not live proof.
01

Component map

One contract

Local whisper, OS, cloud, and remote LAN engines all answer the same /v1/health, /v1/session, and /v1/transcribe + WS message contract. A mode change is a transport change, not a second app.

One emission point

Engine messages go through bus.js; the parent mirror and every WebSocket are subscribers. That is why the rail survives a dropped renderer socket and why history sees the same finals.

One refusal rule

A provider, model, key, consent, or transport that is missing must refuse with a sentence. A local process under a cloud label is forbidden by test and by code.

03

Audio path, exactly

No pause

The 15 s cap guarantees a final even during continuous speech. First card ≈ 15 s audio + inference. With tiny that is ~16 s; a CPU large model can fall behind.

Normal sermon pause

500 ms of silence finalizes the segment. First card ≈ 0.5 s + inference (~1–3 s). This is the designed live path.

Backpressure

The renderer queue is bounded to 30 s and drops the oldest frames. The engine serializes transcribes; a slow model becomes latency, not unbounded memory.

04

Verse detection

Strict detector order

  1. Spoken reference. “Isaiah chapter 45, verse 2” normalizes to Isaiah 45:2. ASR punctuation is handled; a comma no longer falls back to verse 1.
  2. Alias table. Misheard book names (“Revelations”, “Corinthian”) resolve through data, with ambiguity disclosed.
  3. Full-text index. When no reference is spoken, the recent 600-character tail is searched against the active translation using the inverted index (IDF + phrase bonus), not a containment counter.

Gates before a card

  • Hallucination gate runs on the newest segment: noise/VAD flags can blank every lane.
  • Confidence = match quality × segment weight; below 0.60 nothing renders.
  • Short tails are refused; one- and two-word queries cannot become a verse.
  • Operator dismissals are per reference; dismissal does not move any output.
  • The card shows the resolved text and translation before Send Live is enabled.
Measured truth: on 24 minutes of real sermon captions the indexed scorer returned only actual references (John 10:35, Numbers 23:19, Genesis 27:38–40). The old containment worker produced four wrong references at 0.62–0.73. On garbled tiny-model ASR, false hits are still possible; production accuracy depends on the ASR model.

06

Cloud · PR #86

Implemented shape

  • Renderer keeps the same PCM loopback WS. Two provider lanes share the contract: OpenAI /v1/audio/transcriptions (multipart) and OpenRouter /v1/responses (JSON base64 input_audio).
  • OpenAI: whisper-1 default, gpt-4o-transcribe opt-in. OpenRouter: google/gemini-2.5-flash default and google/gemini-3.8-flash; unknown/provider-mismatched models refused.
  • Keys are provider-scoped: keytar → separate AES-256-GCM 0600 fallback files; renderer sees only {configured} per provider.
  • Explicit, session-scoped egress acknowledgement. Leaving Cloud revokes it.
  • Missing provider/key/consent or Test Mode refuses before any fork.

Why it is not production yet

  • No live OpenAI or OpenRouter key was available; auth, billing, retention, rate limits, and real sermon quality are unverified for both lanes.
  • Cloud audio leaves the building. The operator must understand that the live feed can contain off-mic speech.
  • PR #86, not merged. No nightly contains it.
  • Error taxonomy is real: cloud-auth-invalid, cloud-rate-limited, cloud-network-error, cloud-bad-response, …
Cloud is a transport, not a label. Until this PR lands, the production build refuses Cloud with where-not-implemented. That refusal is deliberately safer than a local engine wearing a cloud badge.
07

Local network · PR #86

Implemented shape

  • Remote speech-engine health-checked at /v1/health with a token; protocol major must match.
  • Renderer dials the remote WebSocket and streams the same PCM frames. No local fork, no fallback.
  • Remote engine gets --allow-lan / LD_SPEECH_ALLOW_LAN=1 plus an explicit token; default remains loopback-only.
  • Endpoint persisted; token session-only.

Security truth

  • No TLS. Raw PCM and the token cross the LAN. Trusted LAN only.
  • The token is a gate, not encryption. A hostile LAN peer can observe traffic.
  • No second physical machine was available; only fake loopback health/WS tests.
  • Cross-host firewall, Wi-Fi loss, reconnect, and port policy remain unverified.
Network is not “only text crosses the network” — the current architecture sends audio to the remote recognizer. The copy now says that plainly. A text-only remote design would be a different product.

OS on-device · experimental

Full recording result

97chunks
0finals
95low-confidence

24 minutes of the actual church recording through Windows System.Speech. One silent skip, one no-transcript, zero usable finals.

What is safe

  • The driver refuses recognition below 0.25 confidence; no wrong verse from low-confidence text.
  • The PowerShell script loops to EOF and reports the minimum confidence across utterances.
  • On clean synthetic audio it works (0.0% WER); on real church audio it does not.

System.Speech 8.0 is a 2006-era recognizer. To make OS on-device real, replace it with WinRT Windows.Media.SpeechRecognition and validate on church hardware. Until then it is an experimental fallback, not a production provider.

Data, history, tuning

Local history

One JSON file per session under <userData>/speech-engine/history/. Capped at 64 MiB / 500 sessions; oldest rotates first; the drive never fills. The repo is never written to.

{
  "schema": 1,
  "sessionId": "...",
  "modelId": "tiny.en",
  "providerId": "whispercpp",
  "where": "local",
  "segments": [ ... ],
  "events": [
    { "type": "suggestion", "lane": "verse",
      "reference": "Isaiah 45:2",
      "detector": "spoken", "confidence": 0.95 },
    { "type": "action", "lane": "verse",
      "action": "send", "reference": "Isaiah 45:2" }
  ]
}

Tuning data

  • Events are whitelist-only: type/lane/action/reference/detector/confidence/code/timestamps. No transcript copy, no audio, no free text.
  • Bounded 2,000 events per session.
  • Export via Preferences → Experimental → Speech → Local tuning data; JSON includes transcript + events.
  • Nothing is uploaded. The export path is shown; the operator copies it deliberately.
  • Erase-all removes history, events, and exports.

What moves 8 → 10

  1. Validate a production model on the actual church PC/mixer feed: WER ≤10–15%, RTF <1.
  2. Ship GPU builds (CUDA/Vulkan/Metal) and macOS engine packaging. CUDA selection is in PR #86; Vulkan and Metal still need real builds.

  4. Test on a physical Windows church PC with a real microphone or dry aux.
  5. Merge + live-test cloud (real key) and network (second machine).
  6. Decide OS on-device: replace with WinRT or keep it explicitly experimental.
